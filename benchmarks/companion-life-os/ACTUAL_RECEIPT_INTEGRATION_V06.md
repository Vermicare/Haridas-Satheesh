# Companion — Actual v0.3 Receipt to v0.5 Correction Integration (v0.6)

**Date:** 2026-10-25. **Evidence type:** fictional, local SQLite software-contract integration only. **Stage:** public Simulation/contract evidence; private implementation maturity unchanged. **PR:** [#10](https://github.com/Vermicare/Haridas-Satheesh/pull/10) (draft, not merged).

## Hypothesis and provenance

Earlier v0.5 correction tests inserted a hand-authored original receipt into the `receipts` table. They did not prove that a receipt **actually generated by v0.3** can be consumed by the v0.5 ledger. This experiment uses the pre-existing, fictional `scenario.json`, `authorization_store_v03.py`, and `correction_ledger_v05.py` without modifying their implementation. Original receipt generation and correction run against the same disposable on-disk SQLite database. All names, timestamps and approvals are fictional.

- **Input/fixture:** existing `scenario.json`; test adaptation supplies the same v0.3 machine-readable scope and fictional timestamps used by the earlier v0.3 tests.
- **Test file:** [`test_actual_receipt_integration_v06.py`](test_actual_receipt_integration_v06.py) — eight integration cases.
- **Short demonstration:** [`demo_actual_receipt_integration_v06.py`](demo_actual_receipt_integration_v06.py).
- **Dependencies:** CPython 3.13; Python standard library (`sqlite3`); GitHub Actions Ubuntu/Windows matrix. Exact patch version, SQLite build and runner image: **TBD** unless captured from logs. Seed: N/A (deterministic fictional input).
- **Baseline:** v0.5 tests seeded original receipts; v0.3 tests did not invoke v0.5 correction.
- **Method:** invoke `FictionalDurableStore.execute` for the original receipt, then `FictionalCorrectionLedger.record` for its correction, and verify durable history across fresh instances.
- **Predeclared checks:** original receipt preserved byte-for-byte at DB row level; action/decision/nonce bound; no correction before original; forged action rejected; pre/post-commit failure injection; 16 concurrent identical correction requests produce one event; second correction is linear and fork rejected.
- **External actions:** zero by construction; no real user, service, task update, or reversal.

```bash
python demo_actual_receipt_integration_v06.py
```

CI runs the new tests alongside the unchanged v0.2/v0.3/v0.5 tests, on Ubuntu and Windows, and uploads the machine-readable demo output. Final cross-platform result and reproducible output digest must be read from a **completed run**, not inferred from source alone.

## Failure/learning and limitations

A v0.5 correction now receives an actual v0.3-generated fictional receipt, rather than a test-seeded stand-in. This closes an **interface-integration** evidence gap only. Tests inject Python exceptions, not physical power cuts. Caller-supplied principal and time are not authenticated. SQLite is not an external transactional action adapter. The event records a requested correction; it **does not undo** a task update. An operator can modify both original and correction records; no independent cryptographic trust anchor or tamper resistance is established. Performance, reviewer burden, identity verification, real connector acknowledgments, real consent, and actual reversal remain **TBD**.

**Next gate:** sandbox identity issuer + trusted timestamp + transactionally recorded outbox/ack for a fictional adapter, with adversarial restart and duplicate-delivery tests. Independent review is required before stage advancement. Reframe as read-only advisory if the added governance complexity cannot be justified by measured benefit.
